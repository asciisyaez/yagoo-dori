## Systematic Review Checklist

### 1. Functional Requirements

- [ ] Implementation logic matches requirements correctly
- [ ] Interface/API matches documented specifications
- [ ] Error scenarios handled with proper feedback
- [ ] Edge cases and boundary conditions validated

### 2. Code Quality

- [ ] Proper typing (strict TS; no unjustified `any`; honors
      `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`)
- [ ] DRY principle - no code duplication
- [ ] KISS principle - not unnecessarily complex
- [ ] Consistent, descriptive naming conventions
- [ ] Complex logic has explanatory comments
- [ ] Files/modules not excessively large
- [ ] Imports organized, unused ones removed

### 3. Architectural Compliance

- [ ] Code follows established patterns from ARCHI.md (TypeScript semantic
      authority, data-as-code, evidence artifacts, v0.1/v0.2 separation)
- [ ] Proper separation of concerns (core logic in `packages/core`, UI in
      `apps/web`, orchestration in `scripts/`)
- [ ] Methodology changes mint new version identifiers instead of mutating
      existing artifacts
- [ ] Consistent with existing codebase style

### 4. Exactness & Claim Discipline

- [ ] All comparisons that establish parity, ties, pruning, or optimality use
      six-decimal signed integer micro-units — no epsilon/tolerance anywhere
- [ ] Outward rounding preserved end-to-end; enclosures never narrowed
- [ ] Ambiguous/unsupported cases fall back (ordered replay / singleton /
      promotion) — never guess, never silently fall through
- [ ] Equality is never pruned; B2 prunes only certified strict central loss;
      unresolved/tied candidates promote to B3
- [ ] No result labeled exact/optimal/global/certified/proof unless its gate
      passed; bounded results named as bounded
- [ ] `certificateEligible=false` and `fullRunAuthorized=false` unchanged
      (unless the ticket's declared gates genuinely passed)
- [ ] Claim A (aggregate) and Claim B (conditional order) not conflated

### 5. Evidence & Determinism

- [ ] New/changed evidence artifacts carry `schemaVersion` and a stable digest
      that excludes timestamps and timing data
- [ ] Generators are deterministic (fixed seeds, ordered iteration); reruns
      reproduce the stable digest
- [ ] Tracked JSON diffs inspected — runtime metadata churn identified and
      explained
- [ ] Failed targets and missed gates reported plainly in artifacts/docs, not
      hidden by corpus selection or combined speedups
- [ ] Parity obligations honored: semantic changes re-execute full corpora
      (`optimizer:parity:bulk`, `optimizer:parity:compiled`), not rehash-only
- [ ] Proof accounting still reconciles declared totals (126,445,821 × 113
      Outfit/team pairs across prunes, evals, and tied finalists)

### 6. Scope & Product Safety

- [ ] v0.1 public surface untouched: no changes to calculator claims,
      rankings, guides, or product UI during optimizer tickets
- [ ] Rankings/guides not regenerated without a methodology/input change
- [ ] Game mechanics, triggers, Bloom assumptions, chart benchmark, rounding,
      and legal-team constraints unweakened (especially not for runtime)
- [ ] No push, tag, deploy, Pages/Actions setting, or visibility change
- [ ] Historical 864-shard plan not executed
- [ ] Epic/ticket status updated only from current evidence; unrelated working
      tree edits preserved

### 7. Error Handling

- [ ] Errors are properly caught and handled
- [ ] Error messages are clear and actionable
- [ ] Failure modes are graceful (build-time failures loud; fallback paths
      honest)
- [ ] Logging/telemetry appropriate (stable fallback reasons, not noise)

### 8. Security (if applicable)

- [ ] Input validation implemented (zod at boundaries)
- [ ] No sensitive data exposed; no hotlinked assets
- [ ] No private APIs, scraping-protection bypass, or account automation
- [ ] No obvious vulnerabilities

### 9. Performance

- [ ] No obvious performance issues; hot paths free of unnecessary work
- [ ] Resource cleanup implemented (workers cancellable, no leaks)
- [ ] Performance claims are measured (p50/p95 on normalized workloads)
      against declared targets, with misses retained as failures
- [ ] No fast-math, approximate reciprocals, unordered reductions, or FP
      reassociation in certificate paths

## Issue Severity Classification

**Critical (Block Deployment)**:

- Security vulnerabilities
- Data corruption risks
- Breaking API/interface changes
- Unsound exactness claims (epsilon comparison, narrowed enclosure, pruned
  equality, unproven dominance credit, false certificate/authorization flags)

**Major (Require Immediate Fix)**:

- Incorrect business logic or game-mechanics modeling
- Significant performance degradation
- Missing error handling or silent fallthrough of unsupported mechanics
- Compilation/build errors
- Nondeterministic or timestamp-contaminated evidence digests

**Minor (Should Fix)**:

- Code style inconsistencies
- Missing documentation
- Code duplication
- Missing edge case handling

**Suggestions (Nice to Have)**:

- Performance optimizations
- Readability improvements
- Additional test coverage

## Review Completion Criteria (Approval Gate)

Minimum for approval:

- [ ] All functional requirements implemented
- [ ] No critical or major issues remaining
- [ ] `pnpm lint` and `pnpm typecheck` pass
- [ ] Affected unit tests pass (`pnpm --filter @yagoo-dori/core test -- <files>`,
      per the TRIP-2 testing gate)
- [ ] Applicable evidence/proof checks pass (parity, metamorphic, reduced
      proof, shard determinism, `pnpm data:validate` — as obligated by the
      change surface)
- [ ] New logic has test coverage (or a coverage-debt ledger entry per the
      hard-to-cover policy)
- [ ] Documentation updated per project standards (ARCHI-rules.md; optimizer
      docs for X-series work)
- [ ] Before ticket completion: the full AGENTS.md verification chain in exact
      order, ending with `pnpm project:status`
